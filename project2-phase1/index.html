SHEET 01

What LangChain is, and what a chain does

Calling an LLM directly is a one-off: you write the whole prompt by hand, send it, and get a blob of text back — no structure, nothing reusable. If I wanted to reuse the same prompt shape for ten different restaurants, I'd be copy-pasting and editing text every single time.

LangChain is a layer on top of that raw API call. It gives you three reusable pieces: a prompt template (a prompt with blanks to fill in), an LLM wrapper (a consistent way to talk to Gemini, Groq, or any other provider without rewriting your code for each one), and a chain — those pieces connected together into one repeatable unit: template → LLM → output.

In SlotWise terms

My Telegram bot's system prompt was one long fixed block of text I wrote by hand. A LangChain version would turn "Greet the guest and ask about {occasion}" into an actual template — swap in occasion = "birthday" or occasion = "business lunch" without touching the rest of the prompt.

LCEL — the syntax that connects the pieces

chain = prompt | llm | parser
chain.invoke({"occasion": "birthday"})

The | just means "then feed into." Read it left to right: build the prompt, then send it to the LLM, then parse what comes back.

SHEET 02

Prompt templates & output parsers

A prompt template is the fill-in-the-blank idea from Sheet 01, written out properly — placeholders like {product_name} get swapped for real values at run time, so you write the wording once and reuse it forever.

An output parser solves a different problem. Left alone, an LLM answers in flowing sentences — great for a human, painful for code. If my SlotWise bot's confirmation message came back as pure prose, my n8n workflow would have no reliable way to grab just the date or just the time. An output parser tells the model "reply only in this exact shape," usually JSON, so the code can read booking.date directly instead of guessing at meaning.

plain prompt

"Your table is booked for Friday at 7:30 PM for a birthday dinner. See you then!"

Readable, but code has to guess where the date starts and ends.

JSON-parsed prompt

{
  "date": "Friday",
  "time": "7:30 PM",
  "occasion": "birthday"
}

Every field is exactly where the code expects it.

A familiar trick

This is basically the more official version of the [BOOKING_CONFIRMED: name=..., date=...] tag I hand-built with regex in SlotWise — LangChain's output parsers (like JsonOutputParser, or a Pydantic model that defines the exact fields you expect) do the same job in a cleaner, built-in way.

SHEET 03

Memory & tool-calling

An LLM has no memory by default — every single call starts from zero, as if it's the first thing you've ever said to it. Memory means keeping a running log of the conversation and feeding that whole log back in with every new message, so the model can refer back to what was said earlier.

Tool-calling is a separate idea: giving the LLM access to real functions it can choose to run — a calculator, a search lookup, a database query — instead of it guessing an answer from what it already "knows." The model itself decides when a tool is needed and what to pass into it; your code just has to make the tool available and hand back whatever it returns.

In SlotWise terms

My Simple Memory node in n8n was exactly this idea — keyed by Telegram's chat.id so each guest's conversation stayed separate. If SlotWise ever needed to check a real calendar instead of offering mock time slots, that would be a perfect case for tool-calling: the LLM decides "I need to check availability" and calls a "check_calendar" function instead of inventing an answer.

SHEET 04

What LangGraph is — chain vs. agent

A chain (Sheet 01) always runs in the same fixed order — step one, then two, then three, no matter what. That's fine for simple tasks, but it breaks down the moment a workflow needs to actually decide something: skip a step, repeat one, or choose between two different paths depending on what just happened.

LangGraph is built for exactly that. Instead of a straight line, you build a graph — a network of steps that can branch, loop, and make decisions. Four core pieces:

node

One step in the graph — a piece of work, same idea as a step in a chain.

edge

A fixed connection: "after this node, always go to that one next."

conditional edge

A decision point: "check the result, then choose which node comes next."

state

The data that travels through the graph, getting read and updated at each node.

a graph with a conditional edge

Where I already used this idea

My SlotWise IF nodes in n8n were doing this exact job, just outside of code — checking whether the AI's reply contained BOOKING_CONFIRMED or HANDOFF and sending the data down a different path depending on the answer. That's a conditional edge in everything but name.

SHEET 05

Orchestrator agents

An orchestrator agent receives a task, works out what actually needs to happen, and routes it to the right specialised agent — but it usually doesn't do the hands-on work itself. Think of it like a restaurant manager: they don't cook the food or seat the guests personally, they decide which staff member should.

This is a multi-agent system — several focused agents sharing state, coordinated by one router/supervisor agent that decides who handles what. It's the exact pattern the next mini-project needs: an orchestrator receives raw data and decides which agent should take it from there.

Why SlotWise didn't need this — yet

SlotWise had one AI Agent doing everything: understanding intent, asking questions, confirming, and flagging handoffs, all in a single system prompt. That works for a single, narrow job. An orchestrator becomes worth it once there are genuinely separate specialities — say, a booking agent, an FAQ agent, and a complaints agent — each with its own focused prompt, and something has to decide which one a message goes to first.

SHEET 06

What I'm taking away from this week

Chains gave me the vocabulary for what I'd already half-built by hand in n8n — prompt templates and output parsers are the "proper" version of hardcoding a prompt and regex-matching a tag out of the reply. LangGraph is the bigger shift: thinking in nodes, edges, and state means designing for decisions and branches from the start, instead of bolting an IF node onto a straight line after the fact. Orchestrator agents are the piece I understand conceptually but haven't built yet — next up.
